01. React JS roadmap
Q. Why Need Of React? What was problem that React JS introduced?
Answer: 

Absolutely. To really understand why React was needed, it helps to understand the pain of web development before React rather than starting with useState() and JSX.

The short answer
React was created because building large, highly interactive web interfaces with traditional JavaScript became difficult to manage.

The core problem was:

As an application's UI became more dynamic, keeping the DOM synchronized with changing application data became increasingly complex.

React introduced a different way of thinking:

Old mindset:

“Something changed. Which DOM elements do I need to manually update?”

React mindset:

“My UI is a function of my data. If the data changes, React figures out what needs to change in the DOM.”

Now let's go back to the beginning.

In the early web, websites were primarily documents.

You had:

<h1>My Website</h1>
<p>Welcome to my website.</p>
The server would generate HTML and send it to the browser.

The browser displayed it.

If you wanted another page:

Home → Server → New HTML → Browser
This was relatively simple.

There wasn't a huge amount of client-side state to manage.

2. Then JavaScript Arrived
JavaScript allowed websites to become interactive.

For example:

<button onclick="changeText()">
  Click Me
</button>

<p id="message">Hello</p>
JavaScript:

function changeText() {
    document.getElementById("message").innerText = "Hello Chakresh";
}
This was great.

You could modify the page without reloading it.

The browser's DOM (Document Object Model) became something JavaScript could manipulate.

3. Web Applications Became Much More Complicated
This is where the real problem started.

Companies began building applications that behaved more like desktop applications.

Think about:

Facebook

Gmail

Google Maps

Twitter/X

dashboards

chat applications

e-commerce sites

Imagine Facebook.

One page may contain:

User profile
     ↓
Posts
     ↓
Likes
     ↓
Comments
     ↓
Notifications
     ↓
Messages
     ↓
Friend requests
Now imagine thousands of things changing.

For example:

User likes post
       ↓
Like count changes
       ↓
Button appearance changes
       ↓
Notification changes
       ↓
Maybe activity feed changes
With traditional JavaScript, developers could easily end up writing:

document.getElementById(...)
document.querySelector(...)
element.innerHTML = ...
element.classList.add(...)
element.classList.remove(...)
Every time the application state changed, developers had to carefully determine:

Which part of the DOM should change?

And that's where complexity exploded.

4. The Real Problem Wasn't JavaScript
This is an important point.

React didn't appear because:

"JavaScript was bad."

JavaScript was extremely useful.

The problem was managing UI state and DOM updates at scale.

Imagine:

let username = "Chakresh";
let likes = 10;
let loggedIn = true;
let notifications = 5;
Your UI depends on all of this.

For example:

username ───────→ Profile
likes ──────────→ Like button
loggedIn ────────→ Login/Logout
notifications ──→ Notification badge
Now change:

likes++;
You need the corresponding UI to update.

A developer could manually do:

likes++;

document.querySelector("#likeCount")
        .innerText = likes;
That's manageable in a small application.

But imagine 10,000 pieces of UI interacting with each other.

5. Facebook Was One of the Major Pain Points
This is where the story becomes interesting.

React originated at Facebook (now Meta).

One of the important engineers associated with its creation was:

Jordan Walke.

He developed the early React prototype while working at Facebook.

But React wasn't simply:

"One guy suddenly invented React."

It evolved through work by Facebook engineers and the wider engineering organization.

React's history is closely connected with Facebook's efforts to solve problems in large, dynamic interfaces.

6. The News Feed Problem
Think about Facebook's News Feed.

Suppose you have:

Post A
❤️ 100 likes
💬 20 comments

Post B
❤️ 50 likes
💬 10 comments

Post C
❤️ 75 likes
💬 30 comments
When somebody clicks Like on Post B:

50 likes → 51 likes
Seems easy.

But the application may have:

News Feed
Notifications
Profile
Friend activity
Messages
Sidebar
Counters
etc.
All of these can potentially depend on application state.

Developers had to reason about:

STATE
  ↓
Which DOM?
  ↓
Which element?
  ↓
What mutation?
  ↓
What happens to other components?
As applications became larger, this became increasingly difficult.

7. The "Cascading Update" Problem
Imagine:

User
 │
 ├── Profile
 │
 ├── Posts
 │     ├── Like
 │     └── Comments
 │
 └── Notifications
Now:

User likes post
This might cause:

Post like count ↑
Notification count ↑
Activity feed changes
Button appearance changes
So one state change can produce multiple UI changes.

Developers were effectively maintaining two things:

Application State
       +
DOM State
And they needed to keep them synchronized.

That's the difficult part.

8. React's Big Idea
React flipped the relationship.

Instead of developers saying:

"Change this DOM element."

React encouraged developers to describe:

"Given this state, this is what my UI should look like."

For example:

function Counter() {
    const [count, setCount] = useState(0);

    return (
        <button>
            Count: {count}
        </button>
    );
}
Conceptually:

State
  ↓
UI
If:

count = 0
React renders:

Count: 0
If:

count = 1
React updates the UI to:

Count: 1
You don't manually write:

document.querySelector(...)
for every update.

9. This Is Where "Declarative UI" Comes In
This is probably the most important React concept to understand.

Imperative programming
You tell the computer how to do something.

Example:

const button = document.querySelector("#counter");

button.innerText = "Count: 5";
You're saying:

Find this element and change its text.

Declarative programming
You describe what the UI should be.

Conceptually:

<button>
    Count: {count}
</button>
You're saying:

The button should display the current count.

React handles the DOM update.

10. React's Mental Model
The fundamental model became:

        STATE
          ↓
       COMPONENT
          ↓
           UI
When state changes:

STATE changes
     ↓
React re-renders
     ↓
React compares UI representation
     ↓
React updates necessary DOM
That's the foundation.

11. What Is the Virtual DOM?
You will hear this everywhere when learning React.

Historically, React introduced a Virtual DOM approach.

Very simplified:

Actual browser DOM:

Real DOM
   ↓
expensive/complex to manipulate repeatedly
React maintains an in-memory representation:

JavaScript representation
        ↓
Virtual DOM
        ↓
compare changes
        ↓
update necessary DOM
Suppose previous UI:

<h1>Count: 0</h1>
New UI:

<h1>Count: 1</h1>
React can determine that essentially:

"Only the text changed."
and update the relevant DOM.

Important modern clarification
Don't reduce React to:

"React is a Virtual DOM library."

That's an incomplete explanation.

The more important innovation was the component + declarative rendering model, with React's reconciliation/rendering architecture handling updates.

12. Components Were Another Huge Idea
Before React, UI code could easily become a giant collection of DOM manipulation logic.

React encouraged breaking UI into components:

App

├── Navbar
│
├── Sidebar
│
├── PostList
│   ├── Post
│   ├── Post
│   └── Post
│
└── Footer
For example:

function Post({ title }) {
    return (
        <article>
            <h2>{title}</h2>
            <button>Like</button>
        </article>
    );

Now:

<Post title="Learning React" />
<Post title="Learning JavaScript" />
<Post title="Learning CSS" />
The same component can be reused.

13. Facebook Had Another Problem: XHP
This part of React's history is especially interesting.

Before React, Facebook had developed a system called XHP.

XHP was designed to make HTML generation safer and more component-oriented, particularly on the server side.

The ideas around components and composing UI influenced the thinking that eventually led toward React.

React then brought a component-based approach into the client-side JavaScript environment.

14. Then Came JSX
Another unusual React decision was:

const element = (
    <h1>
        Hello Chakresh
    </h1>

At first glance, developers thought:

"Why are HTML and JavaScript mixed together?"

But React's philosophy was different.

Instead of separating UI by file type:

HTML
CSS
JS
React encouraged organizing code around components.

A component could contain:

UI structure
+
logic
+
state
For example:

function UserCard() {

    const name = "Chakresh";

    return (
        <div>
            <h2>{name}</h2>

Everything related to that component is together.

15. When Was React Created?
The early React work happened at Facebook around 2011–2012.

The technology was publicly introduced at JSConf US in May 2013.

Jordan Walke is widely credited with creating React.

The original project grew from Facebook's internal engineering work on UI development.

React was initially open-sourced by Facebook in 2013.

16. React Wasn't Immediately Popular
This is another interesting part of the story.

When React appeared, many developers were confused by JSX.

The famous reaction was essentially:

"HTML inside JavaScript?!"
Because traditional thinking was:

HTML → structure
CSS → style
JavaScript → behavior
React proposed something closer to:

Component
├── structure
├── behavior
└── state
That was a significant conceptual change.

17. Why Did Developers Eventually Like It?
Because the complexity shifted.

Traditional approach
Developer thinks:

Something changed.

What DOM element changed?

Which other elements depend on it?

Do I need to update another element?

Did I forget something?

What happens if another event changes the same thing?
React approach
Developer thinks:

What is my state?

Given this state,
what should my UI look like?
That is a much more manageable mental model for large applications.

18. Let's See the Difference
Old-style DOM manipulation
let count = 0;

function add() {
    count++;

    document.querySelector("#count").innerText = count;
}

function remove() {
    count--;

    document.querySelector("#count").innerText = count;
}
You explicitly manipulate the DOM.

React
function Counter() {

    const [count, setCount] = useState(0);

    return (
        <>
            <h1>{count}</h1>

            <button onClick={() => setCount(count + 1)}>
                Add
            </button>

            <button onClick={() => setCount(count - 1)}>
                Remove
            </button>
        </>
    );
}
You describe the UI:

<h1>{count}</h1>
and update state:

setCount(count + 1);
React takes responsibility for bringing the UI in line with the state.

19. The Real Problem React Solved
Here's the deepest way to understand it:

Problem
UI synchronization

You have:

Application State
       ↓
      UI
But state constantly changes:

State A
  ↓
State B
  ↓
State C
  ↓
State D
The UI must continuously stay synchronized.

React's abstraction essentially says:

UI = f(state)
Meaning:

The UI is a function of the current state.

This is the idea you should remember.

It was a different architecture for thinking about UI.

A component in React is a reusable piece of UI that contains the logic and structure needed to display part of your application.

The easiest way to understand it is:

Component = a small, reusable building block of a React application.

Think of a website like a house 🏠

A house has:

House
│
├── Door
├── Window
├── Kitchen
├── Bedroom
└── Bathroom

Similarly, a React application can be divided into components:

App
│
├── Navbar
├── Sidebar
├── ProductList
│   ├── ProductCard
│   ├── ProductCard
│   └── ProductCard
└── Footer

Each part can be a React component.

1. Your first React component
function Welcome() {
    return <h1>Hello Chakresh</h1>;
}

Here:

function Welcome()
       ↓
   Component

And:

return <h1>Hello Chakresh</h1>;

is the UI that this component describes.

You can use it inside another component:

function App() {
    return (
        <div>
            <Welcome />
        </div>
    );
}

Notice:

<Welcome />

This is how you use/render a component.

2. Why do we need components?

Imagine you are creating an e-commerce website.

Without components, you might have one huge file:

App.jsx
│
├── Navbar code
├── Product code
├── Cart code
├── Login code
├── Footer code
├── Sidebar code
└── ...

As the application grows, this becomes difficult to manage.

Instead:

src/
│
├── App.jsx
│
└── components/
    ├── Navbar.jsx
    ├── ProductCard.jsx
    ├── Cart.jsx
    ├── Login.jsx
    └── Footer.jsx

Now each component has a specific responsibility.

3. Components are reusable

Suppose you create:

function ProductCard() {
    return (
        <div>
            <h2>iPhone</h2>
            <p>₹70,000</p>
        </div>
    );
}

You can use it multiple times:

function App() {
    return (
        <div>
            <ProductCard />
            <ProductCard />
            <ProductCard />
        </div>
    );
}

You don't have to write the entire product-card HTML three times.

That's reusability.

4. But there's a problem

If every ProductCard shows:

₹70,000

how can we make each card different?

For example:

Same component:

ProductCard
     │
     ├── iPhone

Different data.

6. Component is basically a function

For beginner-level React, remember:

A functional component is a JavaScript function that returns UI.

Example:

function Header() {
    return <h1>My Website</h1>;
}

JavaScript function:

function add(a, b) {
    return a + b;
}

React component:

function Header() {
    return <h1>My Website</h1>;
}

The difference is that the React component returns JSX describing UI.

7. One important rule

React component names should start with a capital letter.

Correct:

function Header() {
    return <h1>Header</h1>;
}

Use:

<Header />

Usually incorrect as a component:

function header() {
    return <h1>Header</h1>;
}

Why?

Because React uses capitalization to distinguish your components from built-in HTML elements.

<div />       // HTML element
<button />    // HTML element

<Header />    // React component
<ProductCard /> // React component
8. The most important mental model

Don't think:

"Component means a function."

That's technically useful, but incomplete.

Think:

A component is an independent, reusable piece of UI that can receive data, maintain state, and describe how its UI should look.

For example:

                 App
                  │
        ┌─────────┼─────────┐
        ↓         ↓         ↓
      Navbar    Counter    Footer
                  │
             ┌────┴────┐
             ↓         ↓
           State       UI
          counter    button

And this connects directly to the React story we discussed earlier:

STATE
  ↓
COMPONENT
  ↓
UI

That's the core idea behind React.

To understand what React does behind the scenes.

React renderer

<h1>Hello</h1>

05. Why you need hooks and project

Why do we need Hooks in React?

The simple answer:

Hooks allow functional components to use React features like state and lifecycle-related behavior.

Before Hooks, React mainly used class components for state.

Before Hooks
class Counter extends React.Component {
  state = { count: 0 };
}

This was more complicated.

With Hooks
function Counter() {
  const [count, setCount] = useState(0);

  return <h1>{count}</h1>;
}

Much simpler.

Why were Hooks introduced?

Functional components originally couldn't easily use things like:

State → useState()
Side effects → useEffect()
Shared context → useContext()
Reusable logic → Custom Hooks

So Hooks allow:

Functional Component
       ↓
    Hooks
       ↓
React features
       ↓
State + Effects + Context + Reusable Logic
Most important idea

A Hook is not just a normal JavaScript function.

For example:

const [count, setCount] = useState(0);

useState() tells React:

"Remember this value for this component and give me a way to update it."

06. Virtual DOM, Fibre and reconciliation
These 3 concepts are connected. Think of them as how React updates the UI efficiently.

1. Virtual DOM

Virtual DOM is a JavaScript representation of the UI.

Example:

<h1>Hello</h1>

React keeps a representation like:

{
  type: "h1",
  children: ["Hello"]
}

When state changes:

State changes
     ↓
New UI representation
2. Reconciliation

Now React has:

Old UI
   ↓
New UI

Reconciliation means:

React compares the old and new UI trees to figure out what changed.

Example:

Old: <h1>Hello</h1>
New: <h1>Hello Chakresh</h1>

React understands:

<h1> is same
Text changed

So it updates only the necessary part of the DOM.

3. Fiber

Fiber is React's internal architecture for performing this work.

It breaks rendering work into smaller units called Fibers.

Conceptually:

Component
   ↓
Fiber
   ↓
Fiber
   ↓
Fiber

Fiber helps React:

organize rendering work
prioritize updates
pause/resume rendering work
efficiently process large component trees

07. Tailwind and Props in React JS
1. Props in React

Props = data passed from parent component to child component.

Example:

function User({ name }) {
  return <h2>Hello {name}</h2>;
}

function App() {
  return <User name="Chakresh" />;
}

Flow:

App (Parent)
   │
   │ name="Chakresh"
   ↓
User (Child)

Think of props as arguments to a component.

function User(name) { ... }  // similar idea

But in React:

<User name="Chakresh" />
2. Tailwind CSS in React

Tailwind = CSS utility classes.

Instead of writing:

.title {
  color: blue;
  font-size: 32px;
  font-weight: bold;
}

You write:

<h1 className="text-3xl font-bold text-blue-600">
  Hello Chakresh
</h1>

So:

text-3xl       → font size
font-bold      → font weight
text-blue-600  → text color
3. Props + Tailwind together

This is where they become useful.

013. Context API crash course with 2 projects
Context API — What is it and Why?

Context API is a React feature used to share data between components without passing props through every level.

The problem: Prop Drilling

Imagine:

App
 ↓ props
Navbar
 ↓ props
UserMenu
 ↓ props
Profile

You need to pass the same user data through components that don't actually need it.

This is called prop drilling.

Context solves this

With Context:

          App
           │
        Provider
           │
    ┌──────┼──────┐
    ↓      ↓      ↓
 Navbar  Profile  Cart
           ↑
       gets data
       directly

Example:

const UserContext = createContext();

function App() {
  return (
    <UserContext.Provider value="Chakresh">
      <Profile />
    </UserContext.Provider>
  );
}

Then Profile can access it directly:

function Profile() {
  const user = useContext(UserContext);

  return <h1>Hello {user}</h1>;
}

No need:

App → Navbar → UserMenu → Profile

to pass the user as props.

Why use Context?

Common examples:

Logged-in user
Theme (dark/light)
Language
App settings
Some shared application state
Easy definition

Context API provides a way to share data across a component tree without manually passing props through every level.

Remember:

Props   → Parent → Child
Context → Provider → Any descendant

27. CORS and debugging in React Project

A CORS error from Appwrite means it doesn't recognize your app's address as an allowed platform. The fix is in the Appwrite console, not your code.

Fix
Open the Appwrite console and select your project.
In the project Overview, scroll to Integrations and open Platforms (older versions: Overview → Add a platform).
Click Add platform and choose Web.
Enter a name (anything, e.g. local) and the hostname localhost. Don't include http://, the port or a path.
Save, then hard-refresh your app (Ctrl + Shift + R).

When you deploy later, add another Web platform with your live domain (e.g. myblog.vercel.app).
